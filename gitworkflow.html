the big picture

What this file actually is

A workflow is a YAML file sitting in .github/workflows/. GitHub watches your repo for the events you list, and when one happens, it spins up a fresh virtual machine, checks your code onto it, and runs the steps you wrote — then throws the machine away.

LevelWhat it controls
workflowThe whole file: its name, what triggers it, shared settings like permissions
jobA group of steps that all run on the same machine, in order
stepOne action: run a command, or use someone's pre-built action
FactWhy it matters
Jobs run in parallel by defaultUse needs: to force an order
Each job gets a new VMNothing installed in job A exists in job B
Steps run in sequenceStep 2 sees whatever step 1 left on disk

Triggers — what starts a workflow

The on: key is a list of events. You can trigger from repo activity, a clock, another workflow, or a manual button click.

ValueFires when…
pushCommits are pushed. Narrow it with branches:, tags:, or paths:
pull_requestA PR is opened, updated, or reopened — the usual choice for running tests before merge
pull_request_targetLike above, but runs with the base repo's permissions/secrets — risky with untrusted PR code, see best practices
scheduleA cron expression, e.g. cron: '0 3 * * *' for a nightly job
workflow_dispatchA person clicks "Run workflow" in the GitHub UI — can accept typed inputs:
workflow_callAnother workflow calls this one as a reusable building block
release, issues, fork…Dozens more GitHub events, same idea

uses: vs run:

What a step can actually do

Inside steps:, each item does one of two things.

run:Shell commands
Executes commands directly in the runner's shell — npm install, pytest, docker build. Use | for multiple lines.
uses:A packaged action
Runs someone else's pre-built action, referenced as owner/repo@ref. Configure it with with:.

Common actionWhat it does
actions/checkout@v4Pulls your repo's code onto the runner — almost every job's first step
actions/setup-node@v4Installs a Node.js version
actions/cache@v4Saves/restores folders like node_modules between runs to save time
actions/upload-artifact@v4Saves build output so you (or a later job) can download it
docker/build-push-action@v6Builds and pushes a Docker image

The @ref part is a version pin — it can be a tag (@v4), a branch (@main), or a full commit SHA. See best practices for which one to actually use.

${{ }}

Passing data around

Workflows talk to themselves through contexts, referenced inside double curly braces.

ContextExampleHolds
github${{ github.ref }}Info about the triggering event — branch, actor, event name
env${{ env.NODE_ENV }}Variables set in env: blocks
secrets${{ secrets.API_KEY }}Encrypted values from repo/org settings — never printed in logs
matrix${{ matrix.node }}The current value in a matrix strategy loop
steps${{ steps.build.outputs.hash }}Output from an earlier step (needs id: on that step)
needs${{ needs.build.outputs.version }}Output from a job this one depends on

with: sends inputs into an action; env: sets environment variables at workflow, job, or step level (narrower scope wins).

before you ship it

Best practices

These are the habits that separate a workflow that works from one that's safe, fast, and cheap to run.

01

Pin actions to a version, ideally a commit SHA

Avoid @main — it can change under you with no warning. Prefer @v4, or a full SHA for third-party actions you don't fully trust.

02

Set the least permission possible

Add permissions: contents: read at the top of the file, then grant more only to the jobs that need it.

03

Never hardcode a secret

Store it in repo/organization Settings → Secrets, and reference it as ${{ secrets.NAME }}. GitHub automatically masks it in logs.

04

Cache what's slow to rebuild

actions/cache for dependency folders can cut minutes off every run — and GitHub Actions minutes cost money on private repos.

05

Cancel stale runs

Add a concurrency: group with cancel-in-progress: true so pushing twice in a row doesn't burn double the compute.

06

Always set a timeout

timeout-minutes stops a stuck job from quietly running (and billing) for hours.

07

Be careful with pull_request_target

It runs with your secrets available even for forked PRs. Never check out and run untrusted PR code under this event without isolating it first.

08

Reuse instead of copy-pasting

Repeated step sequences become a composite action; repeated whole workflows become a reusable workflow called via workflow_call.

09

Lint the YAML before you push

Tools like actionlint catch typo'd keys and bad expressions before GitHub does.
